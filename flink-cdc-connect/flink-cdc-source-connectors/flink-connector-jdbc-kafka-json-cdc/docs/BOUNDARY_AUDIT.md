## 1. 这个连接器在做什么（30 秒背景）

连接器把数据库里的变化搬到别处（比如数据仓库）。干活分两步：

1. **全量（快照）**：把数据库里**此刻已有的数据**整体读一遍。
2. **增量（流式）**：之后**新发生的变化**，一条一条实时搬。

麻烦出在交接点：全量不是一眨眼读完的，它要读一小会儿。**就在读的这几秒里，数据库可能又变了。** 这些「读的过程中新发生的变化」，两头都不靠——既不在全量里，又比增量开始得早。

处理办法是 **回填**：全量读完之后，把「读的过程中新发生的变化」再补读一遍。回填 + 增量 = 数据一条不丢。

于是交接点上，同一条变化可能有两个来源：**回填发一遍，增量再发一遍 → 下游收到两遍（重复）。** 我们要防的，就是这个重复。

每条变化自带一个「发生时间」，报告里叫 `es`（一条普通消息的时间戳）。

---

## 2. 虚惊一场：F1 其实不会重复

我们先担心了一个很具体的场景：全量读到哪一刻为止，会记一个分界线（叫 **HIGH**）。假如有一条消息，它的发生时间**恰好等于分界线**——这一条，回填会发一次，增量会不会**再发一次**？

我们把这个判断逻辑用**真实数据跑了一遍**，结果：**不会。**

原因是消息排序上有个很巧的细节：真实消息永远排在「分界线标记」**前面**，哪怕两者时间相同。所以那条边界消息：

- 回填发一次；
- 增量即使读到它，也会被自己的检查逻辑拦下（因为它的时间和分界线相同，不算"越过"分界线）。

**结论：只有一个大块（不分块）的时候，本来就完美——不多发，也不漏发。** 我们初稿写进报告里的"F1 双发"是一个错误的判断，已经更正。

## 3. 真正的问题：F4 多分区乱序会重复

增量读有个「快车道开关」：一旦它看到任何一条**比全量覆盖更新的**消息，就认为"从现在起全是新数据"，**不再逐个检查**，来了就发。

单队列时这样没问题：老消息肯定先到，开关没打开前就被正常检查掉了。

但 Kafka 把消息分散在**好几个队列（分区）**里，**跨队列的顺序不保证**。举个具体例子：

- 队列 A（热闹）：先送来一条新消息 → **快车道开关被打开**；
- 队列 B（冷清）：才慢吞吞送来一条**旧**消息——而这条旧消息，**回填早就发过了**。

开关已经打开 → 这条旧消息不再被检查 → **又被发了一遍 → 重复。**

这就是 F4 的真面目：**消息跨队列乱序到达时，可能把已发过的旧消息再发一遍。**

---

## 4. 怎么修的：两道闸门

思路一句话：**在增量入口，把「回填已经发过的」再拦一道，让它到不了下游。**

### 第一道闸（Tier 1）：太老的，一律拦下

增量路径上，任何一条消息，只要它的发生时间**不晚于全量覆盖的最早时刻**，直接扔掉——这些数据回填早就处理过了。

- 覆盖场景：只有一个大块（不分块）时，这是唯一要拦的。
- 好处：不管快车道开关有没有打开、消息乱不乱序，这道闸都成立。

### 第二道闸（Tier 2）：属于某块、且没超过那块覆盖时间的，拦下

一个大表会被切成**几块**分别全量读，每块各自记了自己的覆盖时刻。此时只看"最早时刻"就不够了——举个例子：

- 第 1 块覆盖到 **3 点**，第 2 块覆盖到 **4 点**；
- 有一条 3 点半的消息，比"最早时刻（3 点）"**新**，第一道闸拦不住；
- 但它在第 2 块的范围里，而第 2 块已经覆盖到 4 点了——**回填已经发过它了。**

所以第二道闸记得**每块的主键范围和它的覆盖时刻**。增量来一条消息，问两件事：

1. 这条消息的主键，属于哪一块？
2. 它的发生时间，还在那一块的覆盖时刻之内吗？

两个都是 → 回填已经发过 → 扔掉。否则 → 新数据 → 放行。

### 两道闸的分工

- **Tier 1**：管「比所有块都老」的。
- **Tier 2**：管「比最早的块新、但没超过自己那一块覆盖时刻」的——这是最容易漏掉的一段，也是当初报告里指出的"边界残留"。
- **真正的新数据**（发生时间超过自己那一块的覆盖时刻）**永远放行**，不受影响。

## 5. 其它几个发现

- **F5（TiDB，天然安全）**：当数据库是 TiDB、用数据库的提交时间戳做边界时，边界时刻是「我们查询的那一瞬间」，而所有消息的提交时间都**严格早于**这一瞬间——**不存在恰好等于边界时刻的消息**。所以这个场景从原理上就不可能重复，什么都不用做。
- **F2（死代码）**：有个类定义了但全项目没人调用。不是 bug，只是没用的代码，留着下次清理。
- **F3（文档过时）**：有两份文档写的窗口区间和实际代码对不上。不是 bug，只是文档没跟上，留着下次订正。
